# TableProof Cloud Deployment

Use Render's free plan for the Spring Boot API and Vercel for the Next.js frontend. This demo deployment does not provision PostgreSQL.

## Before Deploying

Push changes from Grow Source to https://github.com/print00/Grow-Source before deploying.

Required cloud pieces:

- Render account connected to the GitHub repository.
- Vercel account connected to the same GitHub repository or authenticated Vercel CLI.
- A production backend URL from Render.
- `NEXT_PUBLIC_API_URL` in Vercel pointing to that backend URL.
- `FRONTEND_ORIGIN` in Render pointing to the Vercel frontend URL.

## Render

Render reads [render.yaml](render.yaml) from the repository root.

1. Push this project to a GitHub repository.
2. In Render, create a new Blueprint from that repository.
3. Render will create only `tableproof-api`, a free Docker web service from [backend/Dockerfile](backend/Dockerfile). No database or paid service is requested.
4. Set `FRONTEND_ORIGIN` to the Vercel frontend URL (without a trailing slash). If the frontend is not deployed yet, temporarily use `http://localhost:3000` and replace it afterward.
5. Keep `JWT_SECRET` generated by Render.

Free web services sleep after 15 minutes without traffic. The next request wakes the backend, which can take time. Accounts, uploads, and category changes reset when the process restarts, including after sleeping. Use sample data for testing.

If you already created paid resources on Render, changing this file does not automatically remove their charges. Review those resources separately in the Render dashboard.

## Vercel

Deploy the frontend from [frontend](frontend).

Environment variable:

```text
NEXT_PUBLIC_API_URL=https://YOUR_RENDER_BACKEND_URL
```

CLI deployment after login:

```bash
npx vercel deploy --cwd frontend --yes
```

Production deployment:

```bash
npx vercel deploy --cwd frontend --prod --yes
```

## Important Current Limitation

The app currently has tenant-aware auth and protected routes, but user registrations, CSV uploads, and transaction changes are still stored in the running Spring Boot process. That is fine for a cloud demo, but not for production because data resets when the backend restarts.

Before real customers use it, replace the in-memory repositories with PostgreSQL-backed repositories using the schema in [db/schema.sql](db/schema.sql).
